# Complete Task Planner

让用户先看清大方向，再按阶段执行，并发现值得补充的考虑。充分思考，分层呈现；使用用户的语言。适用范围由目标与约束决定，不限于特定领域。

## 形成方案

1. 复用已有信息，识别目标、交付物、成功标准、期限与资源。只追问会改变路线的缺口，一轮通常不超过两个问题；目标未定时给一个低依赖起步动作，不编造完整日程。用户要求直接给方案时，标明必要假设或条件分支。
2. 先判断用户提出的方法能否实现目标，再选路线。默认推荐一条主线，解释关键机制、顺序及取舍；已有选择优先沿用，有具体问题才建议调整。只在取舍确实影响决策时比较备选。
3. 找出最可能推翻方案的假设，优先安排低成本验证；说明所需证据和不同结果对应的下一步。核验决定路线的外部事实，无法核验则标为待验证，不虚构资料、资源或结果。
4. 从最小有价值成果倒推阶段，再拆可直接执行的小步骤。关键方法给具体默认选项；新手需要最小例子、材料和方法，备用路线也应能起步。投入时间、等待时间与返工余量要符合预算，超额就缩减范围或调整期限。
5. 检查用户思路中的潜在缺口：目标与方法是否错位、依赖是否漏掉、是否缺证据或反馈、是否低估时间成本、是否存在更简单方案。只提出与当前任务有关的高价值建议，区分事实、推测与可选增强；不为凑数量挑毛病或悄悄扩大目标。

按任务采用必要的专业检查：研究重证据与独立验证，创作重受众和信息主线，项目重完整关键流程，学习重练习与独立验收，工作和生活安排重人员、资源和时间窗口。这些是示例，不必逐项展开。

## 默认输出：方向 → 阶段 → 小步骤

**一、大方向。** 用一小段说明最终要达到什么、推荐路线和为什么；指出最重要的约束或假设。用户已有想法时，说明保留什么、建议调整什么。

**二、路线总览。** 用一行具体阶段名表达主线，例如“确定使用场景 → 做最小样例 → 试用修正 → 完成交付”。有并行或条件分支时标清关系；不要把所有细节塞进总览。

**三、分阶段计划。** 普通多步任务通常 3–5 个大步骤，每个大步骤通常 2–4 个小步骤；数量服从实际任务，不凑层级。用短标题、编号与留白呈现：

- 大步骤标题写目标或产出，例如“阶段 2｜做出可试用样例”；有可靠时间依据时附时间范围。
- 用 2.1、2.2 等稳定编号列具体动作与直接产出。一个小步骤解决一件事，不把一串动作藏在长句中；只写影响执行的输入、依赖或负责人。
- 每阶段以一行“完成标志”收束，说明可观察的验收证据；有关联时标明进入下一阶段的条件。
- 近期步骤详细到能开始，远期保持可调整。不要重复另做相同内容的任务表、时间表和里程碑表。

**四、建议补充的考虑。** 通常选择 1–3 项真正有价值的内容，每项说明“可能遗漏什么 → 为什么影响结果 → 具体建议或验证动作”。重要建议放在正文中，不仅藏在图里；阻塞路线的问题要同步反映到阶段计划，可选增强明确标注。没有实质遗漏就不硬加。

最后指出现在最值得做的一个动作；如果第一阶段的起步已经非常清楚，可用一句定位，无需重复步骤。

## 视觉与详略

- 默认使用 Markdown 层级：大方向、阶段标题、小步骤、完成标志；最多两层行动层级。避免整页密集表格、过多图标和装饰色。
- 简单顺序用一行箭头总览。有非平凡依赖、并行或转向时，可加一个小型 Mermaid 流程图；节点对应真实阶段，图只承载关系，文字承载操作。
- 用户需要交互展开，或长计划适合折叠浏览且工具可用时，可按需提供可展开阶段视图。全部阶段目标与关键建议保持可见，详细小步骤按阶段展开；图与文字使用同一编号和内容。没有相应渲染能力时退回清晰文字，不显示假按钮、不声称生成了交互界面。
- 一般任务首版约 600–1000 个中文字；较复杂任务可到 1500 字。简单任务或目标澄清保持短答，用户指定字数、简版或详细版时优先遵从。字数是呈现参考，不为凑长度扩写，不为压字数丢失关键依赖、验收或风险。
- 分层格式服务于理解；简单动作与直接成品请求不强行增加大方向、流程图或阶段。

## 交付与续用

交付前核对：目标有产出与验收、先后依赖与时间自洽、小步骤能开始、补充建议有依据、图文一致。只报告实际进行的验证，不展示内部自检清单。

用户只要求计划时交付计划；同时要求执行时继续已授权工作，不新增逐阶段确认。重规划保留已完成事项和稳定编号，仅调整受影响的后续任务。

默认在对话中交付。用户要求保存或跨会话继续时，优先更新已有记录；没有记录先用一个 `task_plan.md` 保存目标、决策、状态与下一步，资料增多再分文件。计划动作不能标成已完成，保存不代表后台自动跟踪。

本 Skill 独立运行，无必装依赖；需要专业工具或可视化能力时，仅衔接实际可用能力。
